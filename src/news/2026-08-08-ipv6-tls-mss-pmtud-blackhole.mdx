*tl;dr: IPv6 TLS to our anycast endpoints was slow and variable; IPv4 was flat. The anycast
hosts run a jumbo (9000) MTU fabric, so the kernel advertised **MSS 8940**. On IPv6 paths
with a smaller MTU, the large TLS flight needed PMTUD — and ICMPv6 "Packet Too Big" is
frequently filtered, with `tcp_mtu_probing=0` there was no fallback, so it stalled. Fix:
enable `tcp_mtu_probing` and clamp the advertised MSS to 1220.*

---

## Symptom

IPv6 TLS handshakes to our anycast RPC endpoints were slow and bounced by a few hundred
milliseconds; IPv4 to the same hostnames was flat. Rarely a hard failure — just latency.

## Root cause

The anycast hosts run a jumbo-frame internal fabric — the bridge the VIPs sit on is **MTU
9000** — so the kernel advertised **MSS 8940**. There was no MSS clamp and
`net.ipv4.tcp_mtu_probing = 0`.

For an IPv6 client whose path MTU is below 1500 (common on v6):

1. The server sends a large TLS ServerHello + certificate in big segments.
2. A segment exceeds a link MTU; that router should return an **ICMPv6 Packet Too Big**.
3. On IPv6, PTB is frequently filtered by firewalls.
4. With `tcp_mtu_probing=0`, the kernel has **no fallback** — it retransmits the too-big
   segment until it times out.

Each lost PTB ≈ one retransmit timeout. IPv4 mostly dodged it: more uniform 1500 paths and
ICMP PTB is less commonly filtered.

One reason it hid for a while: **ICMP ping has no ports, so its ECMP hash is constant** — it
takes one path and stays clean, while TCP hashes on the source port and spreads across every
path. Ping said 0% loss the whole time. Monitor with real TCP + TLS, not ping.

## The fix

Two host-side changes on every anycast node, both reversible:

```bash
# 1) let the kernel recover from a PMTUD black hole by probing instead of stalling
sysctl -w net.ipv4.tcp_mtu_probing=1
sysctl -w net.ipv4.tcp_base_mss=1220

# 2) clamp the server's outbound segments to fit any v6 path >= 1280, on the incoming SYN
ip6tables -t mangle -A PREROUTING -p tcp --tcp-flags SYN,RST SYN \
  -d <anycast-vip> -j TCPMSS --set-mss 1220
```

Clamp on the **incoming SYN** (`PREROUTING`, `-d VIP`): the oversized flight is
server→client, sized by the *client's* advertised MSS, so shrinking that is what fits the
path. Don't just lower the interface MTU — that breaks the jumbo fabric the rest of the
platform depends on.

## Result

IPv6 TLS went from bouncing to **flat ~290ms** — the clean 3×RTT baseline for the path.

## Also found in the same investigation

Chasing this surfaced an unrelated but real bug: our RPKI ROA for the parent block had
**maxLength `/32`** while we announced `/48` and `/40` more-specifics — making those
more-specifics **RPKI-invalid (`invalid_length`)** and droppable by any network enforcing
route origin validation. It wasn't the cause of the latency, but it was worth fixing: we
published a ROA covering the `/40` and now originate the valid `/40`. The lesson is simple —
**set your ROA maxLength to the longest prefix you actually announce, and never announce
longer than it**; the covering aggregate is your safety net while validators refresh.

## Lessons

- **Never let a jumbo interface MTU leak into the MSS of an internet-facing service.** Clamp
  it. IPv6 is far less forgiving of PMTUD failure than IPv4.
- **Enable `tcp_mtu_probing`** on anything terminating public TLS — it's the safety net for
  the filtered-PTB reality of the modern internet.
- **Ping can't see a per-flow fault.** Monitor with real TCP + TLS over varied source ports.
